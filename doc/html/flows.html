    四条主要链路

    系统运行时只有四条值得记住的路径，其余都是它们的变体。 每条都标出"谁调谁"和"状态在哪里落下来"。

    链路一 · 发一条消息

    ChatMain 输入框 │ onKeyDown / 发送按钮 ▼ store.send(content) ← use-chat-store.ts │ ├─1─ 若当前无对话，先 createConversation() │ ├─2─ 一次 setState 写入两条消息： │ userMsg（完整内容） │ reply（content=""，streaming=true） ← 占位，UI 立刻显示光标 │ ├─3─ 发送中：requestAnimationFrame 节流的 flush() │ 把累积的 delta 追加到 streaming 那条上 │ 每帧最多写一次 state，避免每个 token 触发整树重渲染 │ ├─4─ streamChat() ────────────────────────> lib/deepseek.ts │ POST /v1/chat/completions stream:true │ onDelta → 正文增量 │ onReasoning → 思维链增量 │ └─5─ 收尾三种结局： · 正常结束 → reply.streaming = false · 抛错 → reply.streaming = false, reply.error = msg（UI 渲染错误卡片） · AbortError → 同正常结束，不报错 store.state 变化 ──> useEffect 防抖 200ms ──> saveState() ──> localStorage

    停止与重新生成

    • stop()：abortRef.current.abort()。fetch 抛 AbortError，被识别为"用户主动停止"而非错误。
    • regenerate()：删掉末条 assistant 消息，用其之前的完整历史重新走一遍 send()。
    • branchFrom(messageId)：以 branchedFrom 记录来源， 复制到该消息为止的全部历史新建一条对话。
    为什么发消息要一次写入两条：如果把 user 消息和 assistant 占位分两次 setState，中间会有一帧只有用户消息、光标还没出现的状态，视觉上像"没反应"。 一次写入让"发送"这个动作在 UI 上是原子的。
    为什么用 rAF 节流而不是每个 delta 都写：一次长回答可能有上千个 SSE 分片。 每个分片都 setState 会让 React 每秒重渲染几十次， 后续 Markdown 解析（react-markdown）成为瓶颈。按帧合并后每帧最多一次。

    链路二 · 执行画板上的一条线

    这是画板的核心能力：材料 →（线的提示词）→ 输出。 runEdge（单跑）与 runTask（跑一组）共用 execEdge() 这一个实现。

    触发来源（三种） ├── EdgeEditor 的「立即执行」 ├── 点击/Enter 一条线 → store.runEdge(edgeId) └── 任务下拉「运行」 → store.runTask(taskId) │ ▼ execEdge(edge, {signal, writtenTargets}) │ ├─1─ 从最新 state 取 source / target 节点 │ 不存在 → "failed"（不是异常，只是跳过） │ ├─2─ inputText = resolveNodeText(source) │ note → contentOverride → excerpt → 源消息正文 │ ├─3─ 拼 content： │ 有 prompt：【材料】\n…\n\n【要求】\n… │ 无 prompt：直接是 inputText │ ├─4─ streamChat({ messages: [单条 user] }) ← 每次执行都是无状态单轮 │ └─5─ 写回 target 节点： contentOverride = result.content runs = [新 NodeRun, ...旧] 上限 50 条 同一节点被多条线写 → 用 "\n\n---\n\n" 拼接，保留各自产出 runTask 额外做的事： · 过滤出 isRunnableEdge(edge) 的边（kind=flow 且 enabled !== false） · for 循环串行，边与边之间不做拓扑串联 · 一条失败不影响其他，最后 toast 汇总 "成功 n / 失败 m"
    为什么不做事流串联（DAG）：串起来后会引入"上游失败下游怎么办""环检测" "部分重跑"三大问题，而这些在当前使用场景里价值不高。每条边独立执行、各自写回自己的 终点，语义简单且可预测——这也是"只跑一条"和"跑一组"能用同一套代码的原因。
    NodeRun 快照的价值：每次执行都记下当时的提示词与输入材料。 之后用户改了线的提示词，历史记录仍然显示当时的值，可以对比"同一个输入在两次不同提示词下的产出"。 失败的 run 也会记录，output 为空、带 error。

    执行中的视觉反馈

    • runningTaskId / executingEdgeId 记在 store 与 BoardPanel，对应边加流动动画（CSS dash 动画）。
    • 任务运行期间 stopTask() 可中断：abort 同一个 controller， 已完成的边结果保留。

    链路三 · 状态怎么存下来

    任意 store 方法 │ 调用 setState(updater) ▼ setRawState(prev => next) ← React 的 useState └─ 同一帧内同步更新 stateRef.current ← 给异步循环读最新值用 │ ▼ useEffect([state]) ── setTimeout(200ms) ──> saveState(state) │ ├─ 成功 → JSON.stringify 写入 │ localStorage["shadcn-chat/state/v1"] │ └─ 失败（配额满）→ console.error + 返回 false └─ 上层 toast 提示一次

    其它独立的存储键

    键内容谁写
    shadcn-chat/state/v1整个 ChatStatestore 防抖
    shadcn-chat/theme"dark" / "light"App.useTheme 立即写
    shadcn-chat/board-width画板像素宽度App 立即写
    shadcn-chat/prompt-history/v2按对话分组的提问历史usePromptHistory
    哪些东西不在 ChatState 里：主题、画板宽度、滚动位置、 当前展开的历史项、边编辑器是开着的——都是纯 UI 偏好或会话级瞬态， 它们要么独立存键，要么干脆不存。这让 ChatState 保持"业务数据"的纯粹性。

    读取时的清理

    loadState() 不只是 JSON.parse，它还做三件事：

    1. 把所有 streaming 置 false（刷新后不可能还在流）；
    2. 迁移旧版 message.favorite → 独立 Favorite 实体（幂等）；
    3. gcBoardRefs() 递归清理悬空引用，并把指向已删除对象的 activeBoardId/activeTaskId/mainView 回退。

    链路四 · 画板几何变更

    这是 v2 重写的核心。原则：拖动/缩放期间不写 store，松手时提交一次。

    用户拖动卡片 │ ▼ React Flow 内部 store（onNodesChange → applyNodeChanges） │ 坐标、尺寸、选中状态全部由框架持有 │ 业务 store 此刻不动 ▼ onNodeDragStop / resize 松手 │ ▼ commitGeometry() ← board-canvas.tsx │ ▼ store.moveNode(id, x, y) / store.updateNode(id, {width, height}) │ ▼ store 更新 → toDoc() 重算 BoardDoc → 画布拿到的 nodes 与框架一致 （因为源数据就是刚提交的那份）

    缩放为什么单独抽 resizeNode

    v1 的 bug："往左拉却向右长"。根因是尺寸由 React Flow 内部算，位置由业务 store 管， 两边各写一半，后者用旧值覆盖了前者。

    v2 的解法：model/resize.ts 的 resizeNode(box, dir, delta) 是唯一决定盒子怎么变的地方。它同时返回新的 x/y/width/height—— 向西/北拉时同步修正原点，所以位置和尺寸永远配套。

    resizeNode({x:100, y:100, w:200, h:100}, "w", dx=-50) → { x: 50, y: 100, w: 250, h: 100 } ↑ 原点左移，宽度增加，右边缘不动

    为什么不在拖动中途写 store

    • 写 store → toDoc() 重算 → 传回画布 → 与框架内部值竞争，出现回弹；
    • 每帧写 localStorage 会卡顿（防抖 200ms 虽能缓解，但仍是浪费）；
    • 中途写会让"撤销一次拖拽"变得困难。
    唯一例外：缩放手柄在拖动中会调用 setNodes 直接改 React Flow 的 store（为了实时预览），但依然不碰业务 store， 松手时才落库。所以"两份真值"只在"框架内部实时预览"这一层存在，且方向单一。

    新建卡片的落点

    由 model/layout.ts 的 placeCard() 决定， 入口统一走 store 的 planPlacement()：

    1. 优先贴分支父卡片（向右偏移 LAYOUT_GAP）；
    2. 其次接同一对话的上一条卡片（向下）；
    3. 都不适用则全画布扫描空位；
    4. 扫描上限用尽则在包围盒右侧新开一列。

    硬约束：绝不重叠、绝不移动已有卡片。任何非法输入（NaN、负尺寸）都被夹紧为有限坐标。
